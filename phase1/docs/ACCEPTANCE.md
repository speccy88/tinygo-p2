# Acceptance gates and honest reporting

## Gate 0 — Host environment and portable checks

Run `make host-test` and `make preflight`. Require all host tests to pass, native macOS arm64 execution on the M2, sufficient local disk, and working developer tools. Preserve the supplied original host report before replacing it with the Mac run; write the Mac report to a separately named copy if needed.

The included results are Linux host tests using standard Go 1.23.2, not TinyGo. They exercise 10,000 randomized arithmetic pairs, edge cases, 138 PTY serial challenges against C firmware, rejection of malformed input, checker fixtures and safety gates. A formatted Go overlay is not a typechecked/linked compiler hook.

## Gate 1 — Actual P2 backend control

Run `make fetch`, `make fetch-go`, `make llvm`, `make backend-control`. Require the locked LLVM revision, version in the 14 family, an actual registered P2 target, and a genuine P2 C object/disassembly. Record the native architecture of host tools with `file` on macOS.

This gate says the P2 backend can compile C addition. It is NOT evidence of Go compilation. If it fails, isolate the LLVM/backend/host compiler before changing the TinyGo probe.

## Gate 2 — Original objective: Go addition → P2 object

Run `make probe` (equivalent to `python3 scripts/project.py probe --stage add`).

Require the hook to compile and execute against the custom LLVM, then produce all of:

- `.work/out/probe-add/go.ll`, generated by TinyGo's existing function builder with a P2 target and P2 data layout.
- `go.o`: ELF32 little-endian, EM_P2=300, relocatable, a nonempty global `p2_add` definition and no unresolved helpers.
- `go.s` and independently generated object disassembly.
- `probe.json` and `checked.json` with matching source and artifact hashes.

Inspect the exported function: exactly two 32-bit parameters, 32-bit result, native C ABI, a real addition/return sequence, no hidden context or runtime allocation. Preserve this gate's result independently. This is a meaningful partial completion even if later gates fail.

## Gate 3 — Expanded leaves and link

Run `make probe-full`. Require both p2_add and p2_mix. The latter tests subtraction, XOR, fixed shifts, OR and addition and makes parameter ordering observable.

Run `make libraries`, `make loader`, `make baseline`, `make firmware`. Verify both ELF images fit the internal HUB memory layout. Inspect the link inputs/map/disassembly: the Go image must get its arithmetic exports from the newly generated Go object. There must be no C fallback in that image.

The C image has marker C and does not claim Go. The Go image has marker G. Merely printing marker G is not enough to pass the next gate.

## Gate 4 — Physical C baseline

Review the actual attached board and profile. Confirm console RX/TX and reset wiring. List serial devices; do not probe multiple unknown devices with writes. Use the exact verified /dev/cu.* device, or auto only with one eligible device.

Run the C hardware test with --allow-ram-reset. This resets the MCU and loads RAM only; it must not be controlling external equipment. Require the READY C 1 marker and correct results for all edge cases plus 128 random pairs. Preserve raw terminal data, operands/nonces, parsed responses and artifact hashes.

Failure here is board/clock/loader/UART/C-toolchain bring-up, not a Go arithmetic failure. Fix this layer before blaming the Go compiler.

## Gate 5 — Physical Go computation

Run the Go hardware test on the same port and profile. Require READY G 1 followed by all correct request nonces and both computed results. Random operands are chosen after the firmware was built, so hardcoded print output cannot satisfy the test.

The arithmetic values are unsigned modulo 2^32. C-vs-Go image identity, request ID, result count, addition and the order-sensitive mixing result must all match. A stale serial transcript, C image, timeout, empty response or PASS banner must fail.

Repeat across three fresh RAM downloads with new operands/nonces. Preserve each run rather than overwriting a single success file. State the actual number of replies and computed results, not an estimated pass percentage.

## Strong negative control after success

Recommended once Gate 5 is stable:

1. Preserve the exact original source and its checksum.
2. Change only P2Add's return to `(a + b) ^ 1` in a controlled workspace edit.
3. Rebuild the full probe and Go firmware. Do NOT change the independent host oracle.
4. Run the RAM-only Go hardware challenge; it must fail on the addition result.
5. Restore the original source byte-for-byte, rebuild, rerun and require a pass.

This tests that the live returned answer depends on the Go function rather than an accidentally linked C replacement. Keep the negative-run log. Do not accept the mutation as the final source, and do not weaken checks to accommodate it.

The host test already demonstrates that omitting the Go definitions causes the non-baseline C harness to fail linking, but that host check does not replace a hardware mutation control.

## Evidence and final report

Run `make evidence`. Write `reports/CODEX_REPORT.md` using this structure:

```
Result: OBJECT_ONLY / FULL_PHYSICAL_PROOF / BLOCKED_AT_<gate>
Host: macOS version, Apple Silicon architecture, memory, tool versions
Connected board/clock/serial evidence:
Source pins and every compatibility patch:
Gate-by-gate commands and PASS/FAIL/NOT_RUN:
Addition-only object identity, symbols and hashes:
Expanded object and linked ELF/map/disassembly:
C baseline result:
Go hardware results across fresh loads:
Negative controls (including deliberate failures):
Exact remaining blocker and reproducible failing command:
Files included in return archive:
Next scope boundary (not implemented in this task):
```

Only `FULL_PHYSICAL_PROOF` means the Go computation was verified on the connected P2. Even then, do not claim a normal TinyGo target, runtime, GC, goroutines, drivers, networking, or multicog scheduling.
